# Agent Note: 围绕现有查看器发展餐厅设计工作台

Status: proposed

[English](2026-10-28-restaurant-design-workbench.md) | 中文

## 问题

[已实现的试用版](../../implemented/feature/2026-10-27-restaurant-design-pilot.zh.md) 支持统一项目持久化、组合平移、几何检查和撤销。[查看器适配器](../../../../restaurant-design/src/page.ts) 会改写 HTML 声明与函数，浏览器桥接也依赖所提供编辑器的内部变量。聊天和预览位于不同标签页。工具反复返回完整项目与全部问题，项目尚无餐厅组件目录、坐席分配、使用空间定义或候选布置。

提供的查看器与 [wy51ai/floorplan-3d](https://github.com/wy51ai/floorplan-3d) 存在大量一致的界面和函数代码，确切派生关系与上游提交尚未确认。源数据包含重复或重叠几何及暂定尺寸；几何检查发现的问题不一定是设计错误，家具对象数也不能用于核定座位容量。

## 提案

继续用 Harness 作为助手运行时，以现有离线查看器作为渲染基础。按以下里程碑发展单项目、单人使用的餐厅设计工作台。本提案扩展试用版，不取代其已实现的决策记录。

### 职责分配

| 所属模块 | 职责 |
| --- | --- |
| Harness | 对话、模型路由、工具执行、附件和可持久重建的模型输入记录 |
| 餐厅项目服务 | 尺寸、对象、组合、规则、候选修改、已接受版本和几何检查 |
| 查看器适配器 | 加载项目、报告选择与编辑请求、显示已接受或候选几何、导出视图 |
| 现有 SVG 与 Three.js 渲染器 | 平面绘制、选择、材质、相机控制和漫游 |
| 交付模块 | 关联版本的方案图、家具与坐席表、待确认资料及导出 |

鼠标编辑和助手调用必须使用相同的项目操作。查看器继续隔离运行，不能直接访问文件、凭据或任意 Host 接口。影响模型判断的约束、选择、截图和结果，必须能通过现有工具、附件和会话机制重建。

### 里程碑 0：来源与数据基线

整合上游代码前，记录比对目标、保留源文件指纹、已知差异和许可证信息。保留提供的离线资源和原始项目数据。对照后选择性吸收上游修改；分发采用的代码时附带[上游许可证](https://github.com/wy51ai/floorplan-3d/blob/master/LICENSE)。

与设计人员核对对象分类、疑似重复项、可布置区域轮廓、门和分区。确认含义前保留现有问题记录。增加尺寸来源和确认状态，区分现场实测、图纸读取和假设值。依赖缺失资料的规则必须报告输入不完整，不能将画布矩形范围当成实测房间轮廓。

### 里程碑 1：完整可用的设计流程

将查看器放到现有 Harness 对话旁边。逐步将函数改写替换为显式适配接口，覆盖项目加载、对象选择、编辑提案、已接受版本、平面 SVG 导出和图像捕获。固定支持的查看器版本，对不支持的导入给出明确错误。保留现有离线渲染行为。

引入已确认的两人桌和四人桌组合模板，以及原子替换组合操作。补充显式解除组合和整体旋转，同时保持已接受的成员关系与相对几何。替换操作必须在发布一个新版本前校验完整结果；失败时保持原布置和历史不变。

给模型提供精简的项目摘要、当前选择、相关规则和问题计数。提交请求时记录所选 ID 与版本，避免“这张桌子”等指代跟随之后的选择变化。需要时按对象或区域读取详情。修改回执返回版本、变更对象及新增、解决或恶化的问题。完整项目导出单独保留。保留任务所需信息，并先用当前餐厅测量请求大小，再设置可配置的结果限制。

以一条完整流程验收：选中两人桌组合，请求换成四人桌，预览候选，通过检查后应用，再撤销。明确的普通编辑可在校验后应用；批量备选方案和明确要求预览的修改，在选择前保持候选状态。提交过期候选时，必须按当前版本重新计算。

### 里程碑 2：餐厅使用与通行规则

记录尺寸和使用空间后，再把小型目录扩展到六人桌组合、卡座、独立餐椅和餐边柜。区分实体占地、就坐、拉椅、开门和检修空间。按组件角色和使用状态定义允许的重叠，不能仅因同属一组就豁免无关碰撞。为组件或已确认的卡座分配明确坐席，保留未知分配的可见状态。统计已配置布置的席位数，不将其表述为已核准的容纳人数。

允许设计人员在平面上标记和编辑矩形禁占区、通道区域，为其命名，并记录项目目标及来源。检查家具和已登记使用空间是否侵入这些区域，返回冲突对象、高亮位置、测量值、目标和输入完整程度。不能把手工预留区域称为自动疏散路线分析。

### 里程碑 3：方案对比与方案交付

针对选定区域生成两个局部备选，例如在保留席位的同时扩大活动空间，或在已录入规则内增加席位。使用已确认组件模板和有界候选搜索，再由模型解释实际测得的取舍。找不到可行候选时如实报告，不宣称全餐厅最优。

保存命名方案版本，对比对象变化、已登记席位、规则问题和待核实尺寸。导出包含矢量平面、指定尺寸、家具与坐席表、截图和项目版本的方案 PDF。明确纸张尺寸与绘图比例，并验证打印结果。交付物标为布置方案图，继续保留完整 JSON 导出。

### 后续施工流程

方案流程验收后，再单独确定施工交付范围。施工交付需要核实的现场资料、完成面标高、构造、安装节点、相关专业系统和专业校审。先根据设计人员实际流程选择并验证一种 CAD/BIM 交接方式，再考虑多平台整合。图片或 CAD 自动识别、厨房机电、多用户协作和写实渲染均不在上述里程碑内。

### 实施顺序与验证

先完成来源和数据核对，再完成替换组合流程，然后扩展目录与通行规则。在已校验的操作上构建备选方案和 PDF 交付。保持模型可配置；Astra 启用以具备对应凭据并通过任务级验证为条件，试用版已验证的模型可继续使用。模型升级不能取代几何或数据校验。

每个实现的里程碑都需要对应的几何和项目测试、具有独立项目文件预期的无密钥会话回放，以及两种视图和历史操作的真实浏览器证据。工具行为改变后重新验证真实模型。新文档格式必须有版本，并通过显式导入生成新项目，同时保留源文件。

## 考虑过的替代方案

### 用新引擎替换当前查看器

当前 SVG 和 Three.js 交互已能支撑试用。餐厅操作尚未得到验证前更换引擎，会增加渲染和交互工作，而组件语义和项目规则仍然缺失。先增加适配器，只有已证明的需求无法满足时再评估引擎。

### 继续扩展 HTML 改写

改写能支持已知试用资源，但新增编辑功能会依赖更多内部名称和调用顺序。显式适配器可以集中这类依赖，并提供稳定测试对象。

### 立即增加 BIM 和施工输出

项目还缺少施工输出所需的实测及专业资料。在资料齐全前实施格式转换，得到的交付物仍不完整。方案 PDF 可以更早验证图面表达与交接。

## 验收标准

- 用户在同一屏幕选中桌椅组合，并要求先预览右移 300 mm 的结果。候选与已接受方案明确区分；应用后两个视图和一个新版本同步更新，撤销恢复原几何。
- 将已确认的两人桌组合换为已确认的四人桌模板时，成员、几何和已登记坐席原子更新。被拒绝的替换能定位冲突，已接受项目保持不变。
- 标出入口禁占区并录入座椅拉出空间后，用户能定位侵入、调整布置，导出平面、清单和版本一致的方案 PDF。
- 未知尺寸、坐席分配和使用空间保持可识别状态，不能把未执行的检查报告为通过。

## 风险

代码相似性不能单独确定上游版本。继承的标签和重叠对象需要确认，视觉模板也可能不符合实际产品。房间包含判断、门扇活动范围所需的几何不同于画布范围和宽泛矩形。候选生成可能找不到可用布置。PDF 的比例、文字和尺寸需要视觉核验。上述里程碑始终保持单写入者和单用户限制。
